このキットの中身で一番価値があるのは、たぶんテンプレートではなくこの章です。テンプレートは読めば真似できますが、**「なぜそう書いてあるか」は自分で踏むまで分かりません。**

以下は約2ヶ月、複数のAIエージェントを日常運用する中で実際に起きたことです。どれも「動かなかった」のではなく、**動いているように見えて間違っていた**のが厄介でした。

なお、罠1・2・4・5は無料のZenn記事でも公開しています。ここでは残りの罠3件を含む8件フルセットを収録しています。

---

## 罠1: 評価役に経緯を教えると、判定が甘くなる

### 何が起きたか

判断をチェックさせる「評価役」のエージェントを作り、こう渡していました。

> これこれこういう理由でこの案を進めたいと思っている。チェックしてほしい。

評価役はほぼ通しました。今思えば当然で、**こちらの期待を先に伝えてしまっている**からです。AIは相手の意図を汲むのが上手いので、「進めたい」と書いた時点で、進めていい理由を探す側に回ります。

### どう直したか

評価役への入力から、**動機・経緯・感情を全部落としました。** 数字と事実だけを渡します。

```
悪い例:
「前から気になっていた案で、そろそろ動きたい。以下を評価してほしい」

良い例:
「以下の数字と事実だけで判定してください。前後の文脈は一切知らないものとして扱ってください」
```

さらに、評価役は**会話履歴を引き継がない独立したエージェントとして起動**します。同じ会話の中で「じゃあ次は厳しくチェックして」と役割を切り替えても、それまでの流れが全部文脈として残っているので、独立性は生まれません。

### 教訓

> 評価の独立性は、プロンプトで「厳しく見て」と頼んで作るものではなく、**渡す情報を物理的に絞ることで作る。**

## 罠2: 発想役に裏取りをさせると、発想が死ぬ

### 何が起きたか

最初は「正確なアイデアが欲しい」と思い、発想役に「必ず根拠を確認してから出すこと」と指示していました。結果、出てくる案が**当たり障りのないものばかり**になりました。

観察していると、裏取りを義務づけた瞬間に「裏が取れそうな案」しか出てこなくなります。つまり**既に誰かがやっていること**しか出てこない。新しい組み合わせは、定義上まだ誰も検証していないので、裏取りを条件にすると最初に消えます。

### どう直したか

発想役の指示書に、はっきりこう書きました。

```
- 事実として正しいかより、面白いか・繋がるかを優先する
- 裏取りは不要。外れていてもいい
- 出したものは良し悪し問わず全部残す（後で選ぶのはこちらの仕事）
```

裏取りは**次の工程（評価役）の仕事**として完全に切り離しました。

### 教訓

> 生成と評価を同じエージェントにやらせると、評価が生成を殺す。順番に通すのは正しいが、**同時にやらせてはいけない。**

## 罠3: アイデアが100個出たのに、1つも形にならなかった

### 何が起きたか

罠2を直した結果、発想役はよく動くようになりました。8回ほど回して、案が約100個溜まりました。

**そして何も起きませんでした。**

毎回「これじゃない」で終わる。案の質の問題だと思って発想の技法を増やしたり、テーマを変えたりしましたが、何回やっても同じ場所で止まりました。

### 原因

つまり研究開発だけがあって、工場と販売が無い状態でした。決定した後の行き先が構造として存在しないので、どれだけ良い案が出ても最後は必ず宙に浮きます。「これじゃない」は案が悪かったのではなく、行き先が無い案はどれも「これじゃない」に見えるという話でした。

### どう直したか

「作って、見せて、数字を集める」だけを担当する役を1つ足しました。ルールは3つです。3日以内で作れる最小の形に絞ること（3日で作れないなら案を分割するか見送る）。作る前に何を計測するか決めること（後から都合よく指標を選ばない）。報告は続行・ピボット・撤退の3択に固定すること。

### 教訓

> アイデアが形にならないとき、原因はほぼアイデアの質ではない。**決定の後工程が組織図に存在しないだけ。**

## 罠4: フィールド名を取り違えて、別の意味の数字で判断していた

### 何が起きたか

自動収集したデータをエージェントに渡していたのですが、その中のある項目を、ずっと別の意味の数値だと思って読んでいました。実際には全く別の指標でした。名前から連想した意味と、実際に入っている値の意味が違っていたのです。しかも数値としては一応もっともらしい範囲に収まるので、出力を見ても間違いに気づけません。

見つけたのは評価役でした。「この数値の分布は、名前から想定される指標として不自然」と指摘してきて、そこで初めて発覚しました。数ヶ月分の判断材料が汚染されていたことになります。

### どう直したか

データを渡すエージェント側にデータ辞書（各フィールドが何を意味するか）を必ず置くようにしました。エージェントに数字を渡す前に、フィールド名ではなく辞書のほうを照合するルールにし、正しい意味の項目は別名で追加して、名前だけで推測できないようにしました。

### 教訓

> AIは渡された数字を疑わない。名前から意味を推測して、そのまま使う。**フィールド名の意味は、人間が保証しないと誰も保証しない。** そしてこの種の間違いは、出力が壊れないので発見が遅れる。

## 罠5: 自動生成を全開にしたら、ゴミが8件量産された

### 何が起きたか

記録から記事の下書きを自動生成する仕組みを作り、対象を全部の記録にしました。「材料は多いほうがいい」と思ったからです。

翌朝、内部向けの作業メモまで無差別に記事化された下書きが8件できていました。どれも公開できる代物ではなく、全部捨てました。

### どう直したか

「何を書くか」は人間が選び、「書く」だけを自動化する半自動の設計に変えました。「これは記事にする価値がある」と判断したものだけを専用の場所に短い企画メモとして置き、自動生成の対象をその場所だけに限定しました。

生成量は激減しましたが、使える下書きの数は増えました。

### 教訓

> 自動化していいのは「作業」であって「選択」ではない。選択まで自動化すると、**出力の量に比例してゴミが増える。**

## 罠6: 記憶を検索させたら、他人になりきってしまった

### 何が起きたか

エージェントに過去の記録を検索して参考にする機能を付けました。すると、あるとき急に別の役職の口調で業務報告を始めました。

原因は単純で、検索で拾ってきた記録が別の役のエージェントが書いたメモだったからです。拾った文章を自分の記憶として読んでしまい、書いた人の人格ごと引き継いでいました。

### どう直したか

検索結果を渡すときに、出自を必ず明示するようにしました。

```
以下は参考資料であって、あなたの記憶ではありません。
書いたのはあなたではありません。
[出典: ○○が2026-06-15に記録]
（本文）
```

### 教訓

> 検索結果をそのまま文脈に入れると、AIは「自分が体験したこと」として扱う。**参考資料と自己の記憶は、明示的に区別しないと混ざる。**

## 罠7: 「何もない」という報告を、後段が勝手に埋めた

### 何が起きたか

処理を多段に分けた構成を試していたときのことです。前段が「特に該当なし」と正直に報告しているのに、後段がそれを受けて「何か懸念がありそうだ」と書き始めました。

前段の出力には無い情報を、後段が創作していたことになります。

### 原因

各段に「必ず出力すること」を暗黙に期待していたからです。空の入力を受け取った段は、空のまま次に渡すという選択肢を与えられていませんでした。何か書かなければいけないと解釈すれば、埋めるしかありません。

### どう直したか

各段の指示書に、明示的にこう書きました。

```
入力に該当する情報が無い場合は、「該当なし」と出力してください。
無い情報を補って出力してはいけません。
```

### 教訓

> 多段構成では、**「何も出さない」を正式な出力として許可する。** 許可しないと、AIは埋める。そして埋めたものは下流で事実として扱われる。

## 罠8: 裏で回していた処理が39時間止まっていた

### 何が起きたか

定期的に走らせていたバックグラウンド処理が、39時間ハングしたままでした。気づいたのは完全に偶然です。

エラーで落ちていれば気づけました。落ちずに止まっていたので、エラー通知も出ず、ログの最終行も正常なままでした。誰も異常だと思わなかったのです。

### どう直したか

各定期処理に最終正常終了の時刻を記録させ、想定間隔を超えても更新されていなければ通知するようにしました。通知は成功時ではなく「来るはずのものが来ていない」時に出す設計です。

### 教訓

> 自動化の一番怖い壊れ方は、エラーではなく**沈黙。** 「動いていること」ではなく「動いていないこと」を検知する仕組みを別に持つ。
---

## まとめ: 8件に共通していたこと

並べてみると、ほぼ全部が同じ形をしていました。

| | 共通点 |
|---|---|
| 罠1・罠2 | 役割を分けなかった（評価が生成を殺す / 経緯が評価を殺す） |
| 罠3 | 役割が**足りなかった**（決定の後工程が無い） |
| 罠4・罠6・罠7 | 渡す情報の**出自と意味**が曖昧だった |
| 罠5 | 自動化してはいけない工程（選択）まで自動化した |
| 罠8 | 失敗が**エラーとして現れなかった** |

そして8件全部に言えるのが、これです。

> **どれも「動いているように見えていた」。**

AIエージェントの運用で本当に危険なのは、止まることではなく、**もっともらしい出力を出し続けながら間違っていること**でした。このキットの設計が「役割を分ける」「渡す情報を絞る」という地味な方向に寄っているのは、それが唯一、間違いを**表に出す**方法だったからです。
